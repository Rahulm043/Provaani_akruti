## 8. Cost Optimization & Context Window Compression Architecture

### A. The Gemini Live Quadratic Cost Curve
In Gemini Live's stateful WebSocket session, prompt tokens accumulate on every turn because the model re-attends to the complete conversation history (system instructions + past audio/text turns):
- **Turn 1 (Run 230):** Prompt = 1,936 tokens | Completion = 183 tokens | Total = 2,119 tokens
- **Turn 2 (Run 230):** Prompt = 2,571 tokens | Completion = 247 tokens | Total = 2,818 tokens
- **Turn 3 (Run 230):** Prompt = 3,039 tokens | Completion = 246 tokens | Total = 3,285 tokens
- **Turn 4 (Run 230):** Prompt = 3,483 tokens | Completion = 230 tokens | Total = 3,713 tokens
- **Turn 5 (Run 230):** Prompt = 4,125 tokens | Completion = 232 tokens | Total = 4,357 tokens

### B. Prompt Optimization Applied in Database
- **Baseline Prompt (Node 1):** 4,895 characters (~1,223 tokens). Accounted for over 60% of all billed tokens.
- **Optimized Prompt (Node 1):** Streamlined to 2,153 characters (~538 tokens) directly in Postgres `workflows` (ID 3).
- **Savings:** **~685 tokens saved per turn** (~3,425 tokens saved over a 5-turn call) with zero loss of clinic facts, doctor credentials, or scheduling constraints.

### C. Server-Side Context Compression via `providerOptions`
- Passing `contextWindowCompression` inside standard `session-update` `config` is rejected by Vercel AI Gateway's schema validator with `1008 (policy violation)`.
- However, Vercel accepts `providerOptions` when minting client tokens via `/v1/realtime/client-secrets`.
- In `/app/api/services/pipecat/realtime/vercel_realtime.py` (`_mint_token`):
  ```python
  payload = {
      "model": self._model,
      "providerOptions": {
          "google": {
              "contextWindowCompression": {
                  "slidingWindow": {}
              }
          }
      }
  }
  ```
- This configuration signals the underlying Gemini Bidi session to apply Google's native sliding window context compression as the context approaches token thresholds.

## 9. Turn-End Latency & Agent Silence Investigation (Root Cause Analysis)

### Incident Report: User Disconnect After Turn 5 (Run 230)
- **Symptom:** Caller asked about WhatsApp details and appointment times in Turn 5, heard the agent finish talking, spoke briefly to clarify, but experienced silence and disconnected the call.
- **Chronological Log Analysis:**
  1. `06:50:50.694`: Gemini transcribed user Turn 5 speech: *"Ah, mujhe pata nahi. Maybe main agar WhatsApp mein thoda detail bhej denge to achha tha..."*
  2. `06:51:00.533`: Gemini delivered 232 audio tokens (~9.5 seconds of synthesized speech), playing over the line until `06:51:08`.
  3. `06:51:06.576` – `06:51:07.457`: User spoke a brief follow-up utterance (~0.88 seconds). At `06:51:07.457`, `VADUserStoppedSpeakingFrame` fired.
  4. `06:51:07.457` to `06:51:10.386`: **The ~2.9-Second Silence Window.** Pipecat's VAD wait timer waited ~2.9 seconds of dead silence before emitting `UserStoppedSpeakingFrame`.
  5. `06:51:10.386`: Caller disconnected due to the prolonged silence. At that exact millisecond, Asterisk closed the audio channel, causing `Failed to write audio frame (consecutive failures: 1/10)` and terminating the pipeline.
- **Root Cause:**
  - **No Tool Call Crash:** Gemini did not crash on a tool call; it asked a verbal follow-up question.
  - **VAD Silence Delay:** Pipecat's VAD end-of-speech silence timeout was set to ~2.5–3.0 seconds. Combined with network round-trip and Gemini's multi-turn prompt processing (~1.5s), total turnaround latency reached ~4.5 seconds, making the agent feel non-responsive.
- **Resolution Implemented & Deployed:**
  - Implemented direct handling of `VADUserStoppedSpeakingFrame` with a 600ms conversational debounce timer (`_delayed_turn_commit(delay=0.6)`) in `DograhVercelRealtimeLLMService`.
  - When speech stops, Silero VAD fires `VADUserStoppedSpeakingFrame` instantly; after a 600ms pause, `input-audio-commit` is dispatched immediately to Gemini Live.
  - If the caller speaks again during the 600ms window, the timer cancels seamlessly without interrupting.
  - Overall turnaround latency is cut from ~4.5 seconds down to **~1.5 seconds**, eliminating the perceived stall.

## 11. Tool Execution Failure Analysis (`send_whatsapp` & `end_call`) and The One-Shot WebSocket Architecture

### A. Symptom Observed during Run 231
- When the caller asked *"WhatsApp mein thoda detail bhej denge to achha tha"* (Can you send details on WhatsApp) and provided their phone number, and later said goodbye, the agent replied verbally: *"Maine aapko WhatsApp par details bhej di hain..."* (I have sent you the details on WhatsApp) and *"Dhanyawad, alvida"* (Thank you, goodbye), but:
  - **No WhatsApp message was dispatched via Wati.**
  - **The call did not disconnect automatically.**

### B. Root Cause: One-Shot Session Configuration in Vercel AI Gateway
1. **Pipecat Frame Lifecycle:**
   - On call initiation, Pipecat issues `StartFrame` to all service nodes, triggering `_connect()` in `DograhVercelRealtimeLLMService`.
   - At the instant `_connect()` ran, `self._formatted_tools` had NOT yet arrived from Pipecat's `LLMSetToolsFrame`.
   - As a result, the initial `session-update` frame sent across the WebSocket contained `tools: []`.
   - A few milliseconds later, `LLMSetToolsFrame` arrived and invoked `_set_tools()`, which attempted to send a **second** `session-update` containing the 4 tool definitions (`send_whatsapp`, `book_appointment`, `end_call`, `transfer_call`).
2. **Cloudflare Edge Proxy Transformation:**
   - Vercel AI Gateway's edge proxy maps Gemini Live bidirectional WebSockets.
   - We verified via standalone reproduction (`test_tool_call_trigger.py`) that Vercel rejects any subsequent `session-update` containing `tools` with:
     ```
     1008 (policy violation) WebSocket transform rejected frame
     ```
   - Because the second frame was dropped, **Gemini Live operated throughout Run 231 with 0 registered tools**.
   - Gemini had no callable function definitions in its session schema, so it could only roleplay the tool call verbally in text/audio without emitting a `function-call-arguments-done` or `function_call` event.

### C. The Solution: Pre-Handshake Tool Synchronization
- Added an asynchronous barrier in `DograhVercelRealtimeLLMService`:
  ```python
  self._tools_ready = asyncio.Event()
  ```
- When `_set_tools()` receives the tool definitions from Pipecat, it formats them and triggers `self._tools_ready.set()`.
- Inside `_connect()`, before establishing the WebSocket connection and sending `session-update`, the service waits up to 600ms:
  ```python
  try:
      await asyncio.wait_for(self._tools_ready.wait(), timeout=0.6)
  except asyncio.TimeoutError:
      pass
  ```
- **Result:** The **INITIAL** `session-update` frame immediately contains all 4 tool schemas (`send_whatsapp`, `book_appointment`, `end_call`, `transfer_call`). No secondary `session-update` is required.
- **Empirical Verification (`test_tool_call_trigger.py`):**
  When registered in the initial `session-update`, Gemini Live immediately triggers the tool when prompted:
  ```json
  {"type": "function-call-arguments-done", "name": "send_whatsapp", "arguments": "{\"phone_number\": \"9876543210\"}"}
  ```
- The updated service has been deployed and verified in container `provaani_akruti-api-1`.
